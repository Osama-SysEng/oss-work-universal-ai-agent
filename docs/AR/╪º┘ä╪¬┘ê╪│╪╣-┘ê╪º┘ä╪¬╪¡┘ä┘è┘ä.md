# خطة التوسع والتحليل

الأرشيف المرفوع من TimescaleDB هو مستودع إضافة ناضج لـ PostgreSQL، وليس طبقة قاعدة بيانات جاهزة للنسخ داخل OSS-Work. استفدنا من الأفكار المناسبة فقط: تخزين الأحداث زمنيًا، hypertables، التجميعات المستمرة، سياسات الاحتفاظ، وخطة توافر عالٍ على مراحل.

| المرحلة | المكوّن | ضبط الأمان والتوسع |
|---|---|---|
| الاستقبال | `TelemetryEvent` | تحقق UUID وtenant وحصر المصدر والنوع وحجم payload |
| التخزين المؤقت | `TelemetryBatcher` | حد أقصى للطابور والدفعة مع عداد drop واضح |
| التخزين الدائم | `telemetry_events` | hypertable وفهارس حسب المؤسسة ومنع التكرار حسب الطلب |
| التدقيق | `audit_events` | سجل أحداث منفصل مع تفاصيل منقحة |
| التحليل | `telemetry_hourly` | ملخص ساعي incremental للوحة التحكم |
| الاحتفاظ | سياسة اختيارية | يجب مواءمتها مع نافذة تحديث التجميع |
| التوافر | نشر تدريجي | تحديد RPO وRTO واختبار الفشل قبل replicas |

تفيد continuous aggregates في تحديث الملخصات تدريجيًا بدل إعادة حساب التجميع كاملًا في كل مرة [1]. ويجب تصميم الاحتفاظ والتحديث معًا؛ حذف البيانات الخام قبل materialization الآمن قد يحذف الملخص التاريخي أيضًا [2]. توفر PostgreSQL سياسة أمن على مستوى الصف، لكن أدوار مالكي الجداول وأدوار BYPASSRLS تحتاج إلى مراجعة خاصة [3].

لا يثبت أي أرشيف أو schema عددًا محددًا من المستخدمين. يعتمد الأداء على شكل الأحداث، ومعدل الكتابة، ونوع الاستعلامات، وفترة الاحتفاظ، والفهارس، والعتاد، والشبكة، وحدود التشغيل. يجب تحديد هدف خدمة ثم قياس throughput وp95 وp99 وعمق الطابور والتشبع والاستعادة بعد الفشل وفقد البيانات تحت حمل واقعي.
